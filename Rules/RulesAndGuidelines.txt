
================================================================================
CORE DEVELOPMENT PRINCIPLES
================================================================================

1. REALTIME UPDATES (REQUIRED WHERE NEEDED)
--------------------------------------------------------------------------------
  - Use Supabase realtime for data that benefits from live updates
   - Use supabase channel subscriptions for live updates
   - Critical tables requiring realtime:
     * schedule_entries
     * schedule_conflicts
     * schedule_generation_logs
     * academic_terms
     * sections
     * teachers
     * venues
     * grades
     * grade_components
     * notifications (grade-post alerts)
   - Student grade views must subscribe to posted-grade updates only
     (status = 'posted')
   - Teacher/admin grade views can subscribe to both draft and posted updates
  - Subscribe on mount and unsubscribe on unmount when realtime is enabled
   - Handle INSERT, UPDATE, DELETE events appropriately

2. SKELETON LOADING (RECOMMENDED)
--------------------------------------------------------------------------------
  - Use skeleton loading for primary data-fetching views
   - Never show blank screens or empty content while loading
   - Use the Skeleton component from components/ui/Skeleton.jsx
   - Match skeleton layout structure to actual content layout
   - Show skeletons during:
     * Initial data fetch
     * Page navigation
     * Form submission with data reload
     * Filter or search operations
  - Use page-appropriate loading UX (skeleton, progress view, or spinner)

3. RESPONSIVENESS (MANDATORY)
--------------------------------------------------------------------------------
   - All layouts MUST be fully responsive across mobile, tablet, desktop
  - Use project-consistent styling (CSS Modules-first; Tailwind optional)
   - Breakpoints to follow:
     * sm  (640px)  - mobile landscape, small tablets
     * md  (768px)  - tablets
     * lg  (1024px) - desktop
     * xl  (1280px) - large desktop
   - Test every page on all breakpoints
   - Mobile-first approach: design for mobile, then scale up
   - Ensure touch targets are at least 44x44px on mobile
   - Stack layouts vertically on mobile, use grid/columns on larger screens

4. STYLING ARCHITECTURE (MANDATORY)
--------------------------------------------------------------------------------
   Separation of concerns:

   CSS Modules handle:
     * Layout and spacing (common in current codebase)
     * Custom button styles
     * Hover effects
     * Transitions and transforms
     * Component-specific animations
     * Complex states

   Tailwind handles (optional):
     * Utility-first helpers where already adopted

   Global CSS (styles folder) handles:
     * Color variables (for reference only)
     * Spacing scale
     * Animation keyframes
     * Typography scale
     * Shadow definitions

5. ANIMATIONS (MANDATORY)
--------------------------------------------------------------------------------
   - All animations defined in styles/animations.css
   - Apply via utility classes or CSS modules
   - Never create one-off animations inline

   Standard animations:
     animate-fade-in       -> page and content entry
     animate-slide-in-right -> modals, sidebars from right
     animate-slide-in-left  -> sidebars from left
     animate-slide-down     -> dropdowns, notifications
     animate-scale-in       -> popovers, tooltips, dialogs
     animate-pulse          -> loading indicators, live status
     animate-shimmer        -> skeleton loading backgrounds

   Animation guidelines:
     - Keep animations subtle and fast (200-300ms)
     - Use ease-in-out or ease-out timing
     - Avoid animations on performance-critical renders
     - Reduce motion for accessibility when needed

6. COLOR SCHEME (MANDATORY)
--------------------------------------------------------------------------------
   Primary theme: RED

   CRITICAL RULE:
   Use HARDCODED hex colors directly in components and CSS modules.
   DO NOT use CSS variables like var(--primary-500) - they don't resolve properly.

   Red Color Palette (HARDCODED VALUES):
     Primary 500 (main red) : #ef4444
     Primary 600 (hover)    : #dc2626
     Primary 700 (active)   : #b91c1c
     Primary 900 (deep accent) : #7f1d1d

   Supporting colors:
     Neutrals : Gray scale for text, borders, backgrounds
     Success  : Green  (#16a34a)
     Warning  : Amber  (#f59e0b)
     Info     : Blue   (#3b82f6)
     Error    : Red    (#dc2626)

   Usage rules:
     - Buttons     : use hardcoded hex in CSS module files
     - Backgrounds : use hardcoded hex (#ef4444, #dc2626, etc.)
     - Text        : use hardcoded hex or Tailwind utilities
     - Borders     : use hardcoded hex or Tailwind border-red-500
     - Sidebar background : use light neutral (white/light gray) to match
                           the main content shell
     - Sidebar accents    : use the same red palette (#ef4444, #dc2626,
                           #b91c1c, #7f1d1d) for active/hover states

   Tailwind integration:
     - Use Tailwind red utilities: bg-red-600, text-red-700, border-red-500
     - These are safe to use and resolve properly
     - Keep usage consistent across project

   Special color exceptions (intentional differentiation):
     - Venue Type Tags:
       * Lecture     : #3b82f6 (blue)
       * Lab         : #a855f7 (purple)
       * Open Area   : #22c55e (green)
       * Off Campus  : #f97316 (orange)
     - Subject Type Tags: each has distinct color per type

   - Log errors to console for debugging

--------------------------------------------------------------------------------
   - Validate on client before submitting
   - Use validation utility functions from utils/validation.js
   - Show field-level errors clearly

--------------------------------------------------------------------------------
   - Use semantic HTML elements
   - Provide ARIA labels where needed
   - Ensure keyboard navigation works
   - Maintain focus management in modals
   - Use proper heading hierarchy
   - Ensure sufficient color contrast
   - Provide alt text for images

--------------------------------------------------------------------------------
   - Minimize re-renders with proper memoization
   - Use React.memo for expensive components
   - Lazy load heavy components when appropriate
   - Optimize images (use Next.js Image component if needed)
   - Debounce search inputs
   - Paginate large lists
   - Index Supabase queries properly

================================================================================
SUPABASE INTEGRATION PATTERNS
================================================================================

1. CLIENT SETUP
--------------------------------------------------------------------------------
   lib/supabaseClient.js  -> browser-side queries, realtime
   lib/supabaseAdmin.js   -> server-side/API routes ONLY
   Never expose service role key to client
   Store keys in .env.local file

2. QUERY PATTERNS
--------------------------------------------------------------------------------
   - Use select() with specific columns, avoid select(*)
   - Use single() when expecting one row
   - Use maybeSingle() when row might not exist
   - Chain filters efficiently
   - Use RLS policies for security

3. REALTIME PATTERNS
--------------------------------------------------------------------------------
  - One channel per table subscription
  - Clean up subscriptions on unmount
  - Handle all event types: INSERT, UPDATE, DELETE
  - Update local state optimistically when possible
  - Show toast notifications for relevant changes
  - For student grade views, expose only posted entries
  - For teacher/admin grade views, allow draft + posted entries with role checks

   Standard pattern:
     useEffect(() => {
       const channel = supabase
         .channel('unique_channel_name')
         .on('postgres_changes',
           { event: '*', schema: 'public', table: 'table_name' },
           (payload) => {
             console.log('[Realtime] changed:', payload);
             fetchItems();
           }
         )
         .subscribe();
       return () => supabase.removeChannel(channel);
     }, [fetchItems]);

4. FILE UPLOAD PATTERNS
--------------------------------------------------------------------------------
   - Upload to storage buckets: teacher-avatars, admin-avatars
   - Generate unique filenames (UUID or timestamp)
   - Store only URL/path in database
   - Set proper bucket policies (private by default)
   - Handle upload errors gracefully
   - Show upload progress when possible

================================================================================
API ROUTE PATTERNS
================================================================================

   CRITICAL: params is a Promise in Next.js 15+
   Always await params before using:

     export async function PUT(request, { params }) {
       const { id } = await params;   // CORRECT
       // ...
     }

     export async function PUT(request, { params }) {
       const { id } = params;          // WRONG - params is a Promise
     }

   Applies to: ALL dynamic API routes (GET, PUT, DELETE, PATCH)

   Standard API route structure:

     import { supabaseAdmin } from '@/lib/supabaseAdmin';
     import { NextResponse } from 'next/server';

     export async function GET() {
       try {
         const { data, error } = await supabaseAdmin
           .from('table_name')
           .select('columns')
           .order('column', { ascending: false });

         if (error) throw error;
         return NextResponse.json({ data }, { status: 200 });
       } catch (error) {
         console.error('[GET /api/route]', error);
         return NextResponse.json(
           { error: 'User-friendly error message.' },
           { status: 500 }
         );
       }
     }

   All API routes must:
     1. Use supabaseAdmin (NOT supabase client)
     2. Await params for dynamic routes
     3. Return NextResponse.json()
     4. Try-catch all operations
     5. Never expose raw DB errors to users
     6. Handle duplicate constraint errors (code 23505) gracefully
     7. Check for references before delete

================================================================================
SERVICE LAYER PATTERNS
================================================================================

   Services use fetch() to call API routes
   Services do NOT call Supabase directly
   Location: app/(admin)/feature/services/featureService.js

   Standard service function:

     export async function getItems() {
       try {
         const res = await fetch('/api/items', {
           method: 'GET',
           headers: { 'Content-Type': 'application/json' },
         });
         const json = await res.json();
         if (!res.ok) throw new Error(json.error || 'Failed to fetch items.');
         return { data: json.data, error: null };
       } catch (error) {
         console.error('[featureService.getItems]', error);
         return { data: null, error: error.message };
       }
     }

================================================================================
PAGE STATE PATTERN
================================================================================

   Standard page.jsx pattern for any CRUD feature:

     'use client';

     import { useState, useEffect, useCallback } from 'react';
     import { supabase } from '@/lib/supabaseClient';
     import PageHeader from '@/components/shared/PageHeader';
     import Modal from '@/components/ui/Modal';
     import ConfirmDialog from '@/components/shared/ConfirmDialog';
     import { ToastContainer } from '@/components/ui/Toast';

     export default function FeaturePage() {
       const [items, setItems]             = useState([]);
       const [loading, setLoading]         = useState(true);
       const [modalOpen, setModalOpen]     = useState(false);
       const [selectedItem, setSelectedItem] = useState(null);
       const [itemToDelete, setItemToDelete] = useState(null);
       const [formLoading, setFormLoading] = useState(false);
       const [deleteLoading, setDeleteLoading] = useState(false);
       const [toasts, setToasts]           = useState([]);

       const addToast = useCallback((message, type = 'success') => {
         const id = Date.now();
         setToasts(prev => [...prev, { id, message, type }]);
       }, []);

       const removeToast = useCallback((id) => {
         setToasts(prev => prev.filter(t => t.id !== id));
       }, []);

       const fetchItems = useCallback(async () => {
         try {
           setLoading(true);
           const { data, error } = await getItems();
           if (error) throw new Error(error);
           setItems(data || []);
         } catch (err) {
           addToast('Failed to load items.', 'error');
         } finally {
           setLoading(false);
         }
       }, [addToast]);

       useEffect(() => { fetchItems(); }, [fetchItems]);

       useEffect(() => {
         const channel = supabase
           .channel('feature_changes')
           .on('postgres_changes',
             { event: '*', schema: 'public', table: 'table_name' },
             () => fetchItems()
           )
           .subscribe();
         return () => supabase.removeChannel(channel);
       }, [fetchItems]);

       return (
         <div>
           <PageHeader title="Feature" subtitle="..." actions={...} />
           <List items={items} loading={loading} />
           <Modal isOpen={modalOpen} onClose={...} title="...">...</Modal>
           <ConfirmDialog isOpen={!!itemToDelete} ... />
           <ToastContainer toasts={toasts} onDismiss={removeToast} />
         </div>
       );
     }

   Time slots:
     07:00-07:30  07:30-08:00  08:00-08:30  08:30-09:00
     09:00-09:30  09:30-10:00  10:00-10:30  10:30-11:00

2. SCHEDULE BLOCK STYLING
--------------------------------------------------------------------------------
   - Background  : subject color
   - Border      : 2px solid darker shade of subject color
   - Border radius: 8px
   - Padding     : 8px
   - Text        : centered, truncate if needed
   - Hover       : slight scale or shadow effect
   - Click       : open edit modal or details

3. SCHEDULE GENERATION
--------------------------------------------------------------------------------
   - Show progress indicator during generation
   - Display summary after completion
  - Show conflict count in summary and provide direct navigation to conflicts
   - Allow manual adjustment after generation
   - Save logs for audit trail
  - Generation strategies:
    * Auto Best (default) tries multiple strategies and keeps the best result
    * Strategy results are included in the generation notes for comparison
    * Manual strategy selection is available in Scheduling Setup

   NSTP Rules during generation:
     - Detect subjects with subject_type = 'nstp'
     - Skip NSTP during engine placement (no schedule_entries row)
     - NSTP is NOT assigned a time slot by the engine
     - NSTP does NOT appear as a timetable block in the schedule grid
     - All OTHER Year 1 subjects = Monday to Friday ONLY
     - saturday_blocked = true is checked before assigning Saturday
       to any regular subject for Year 1 sections
     - NSTP can still appear in Course Code tables/reports via
       extra-subject mapping for first-year section contexts

   PE / PATHFit Rules during generation:
     - Detect subjects with subject_type = 'pe'
     - Venue assignment priority:
       1. PE AREA (Open Area / PE) - PRIMARY
       2. CONFERENCE HALL (Open Area / Shared Activity) - FALLBACK
       3. If both occupied - mark as CONFLICT/UNASSIGNED
     - Time is flexible (not fixed) - assigned during generation
     - Duration: 2 hours per session, once per week (single_day)

   BSHM Lecture-Lab Rules during generation (UPDATED):
     - Detect subjects with subject_type = 'lecture_lab'
     - For confirmed BSHM combined subjects, use combined_lec_lab:
       * HPKITCHEN
       * HEBREPAS
       * HEBARBEV
       * HEHOUSEKEEPING
       * HEWEST
     - For confirmed BSHM split subject, use split_lec_lab:
       * HPRESEARCH
     - Other BSHM lecture_lab subjects from curriculum guide need
       confirmation from real schedules before finalizing pattern:
       * HPLODGING
       * HEFNB
       * THEFRONTOP
       * HEDESIGN
       * HEASIAN
       * HPRMICE
       * HPBUSTECH
       * HPERGONOMICS
       * HECATMA

4. CONFLICT DETECTION
--------------------------------------------------------------------------------
   - Check teacher conflicts  (same teacher, same time, same day)
   - Check room conflicts     (same room, same time, same day)
   - Check section conflicts  (same section, same time, same day)
   - Check venue type mismatch
   - Check Saturday restriction for Year 1 sections
     (regular subjects cannot use Saturday if saturday_blocked = true)
   - Same subject code alone  = NOT a conflict
   - Display conflicts with clear descriptions

KNOWN GOTCHAS
================================================================================

   1.  PageHeader prop is "actions" not "action"
   2.  Toast uses named exports only (no default export)
   3.  Skeleton uses default export for base component
   4.  params must be awaited in API routes (Next.js 15+)
   5.  supabaseAdmin for API routes, supabase for client/realtime
   6.  User must be authenticated for RLS queries to work
   7.  academic_terms has partial unique index:
       only one active term allowed at a time
   8.  When setting a term to active, deactivate all others first
   9.  Channel names must be unique per subscription
   10. Always call fetchItems() after successful mutations as backup
   11. NSTP subject_type = 'nstp' (added to enum in Supabase)
   12. NSTP: lec_units = 0, lab_units = 0, credit_units = 3 (manual)
   13. NSTP delivery_pattern = 'single_day' (auto-set, locked)
   14. NSTP is skipped by the engine (not inserted into schedule_entries
       timetable blocks); it can appear in Course Code lists/reports
       via extra-subject mapping for first-year sections
   15. saturday_blocked = true auto-set for all Year 1 sections
   16. Regular Year 1 subjects must NOT use Saturday
   17. PE subject_type = 'pe' (added to enum in Supabase)
   18. PE: lec_units = 0, lab_units = 0, credit_units = 2 (manual)
   19. PE delivery_pattern = 'single_day' (auto-set, locked)
   20. PE venue: PE AREA primary, CONFERENCE HALL fallback
   21. PE duration: 2 hours, once per week, time is flexible
   22. Curriculum version delete requires typed confirmation "DELETE"

DEVELOPMENT WORKFLOW
================================================================================

1. BEFORE CODING
--------------------------------------------------------------------------------
   - Understand the feature requirement
   - Check if similar component exists
   - Plan responsive layout
   - Identify data dependencies
   - Check Supabase schema

2. WHILE CODING
--------------------------------------------------------------------------------
   - Write component structure first
   - Add Tailwind for layout/responsiveness
   - Create CSS module for custom styles
   - Implement loading state with skeleton
   - Add realtime subscription if needed
   - Test on mobile, tablet, desktop
   - Add error handling
   - Add accessibility attributes

3. AFTER CODING
--------------------------------------------------------------------------------
   - Test all user interactions
   - Test edge cases (empty data, errors, slow network)
   - Verify animations are smooth
   - Check color consistency (use hardcoded hex colors)
   - Verify responsive behavior
   - Test keyboard navigation
   - Check console for errors or warnings

COMMON MISTAKES TO AVOID
================================================================================

   1.  Forgetting realtime subscriptions on data tables
   2.  Not showing skeleton loading states
   3.  Using CSS variables instead of hardcoded hex colors
   4.  Not testing mobile responsiveness
   5.  Mixing Tailwind and CSS module responsibilities
   6.  Not cleaning up subscriptions on unmount
   7.  Exposing raw error messages to users
   8.  Not disabling buttons during submission
   9.  Not handling empty states gracefully
   10. Inconsistent animation usage across pages
   11. Using supabaseAdmin in client components
   12. Not awaiting params in Next.js 15+ API routes
   13. Using "action" instead of "actions" in PageHeader
   14. Importing Toast as default export
   15. Forgetting Year 1 saturday_blocked rule for regular classes
   16. Assuming NSTP should be generated as timetable blocks
       (engine skips NSTP; show it via Course Code/report extras instead)
   17. Auto-computing credit units for NSTP subjects
       (must be manual input: 0 lec + 0 lab + 3 credits)
   18. Forgetting PE venue fallback rule (PE AREA -> CONFERENCE HALL)
   19. Not validating max_teaching_days before adding availability
   20. Assuming teachers are locked to departments
       (they can teach any program)
   21. Not persisting multi-select state across filter changes
   22. Assuming all BSHM lecture_lab subjects use the same pattern
       (some are combined, some split, some still need confirmation)
   23. Showing draft component grades to students
       (students should see posted only)
   24. Computing final_grade from unposted component values
       (compute/publish from posted values only)
   25. Assuming realtime means instant while teacher is offline
       (updates arrive after teacher sync)
